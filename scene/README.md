# Gallery scene pipeline

The hero's 3D rooms are generated by script in Blender, lit with pre-computed
(baked) lighting, and exported to glTF for the website. Nothing here runs when
a visitor loads the page; it only runs when the 3D rooms change.

Blender lives in `tools/` (portable 4.5 LTS, not committed). Shortcut used below:

```bash
B="tools/blender-4.5.15-windows-x64/blender.exe"
```

| Step | Command | Time on this laptop |
|---|---|---|
| 1. Download CC0 assets (Poly Haven) | `node scene/tools/fetch-assets.mjs` | 1 min |
| 2. Build the rooms | `$B -b --factory-startup -P scene/build_scene.py` | 30 s |
| 3. Preview stills along the path (optional) | `$B -b scene/out/gallery.blend -P scene/preview.py -- 0 0.5 1` | 15 s each |
| 4. Bake lighting + reflection maps | `$B -b scene/out/gallery.blend -P scene/bake.py -- --samples 160` | ~1.5 h |
| 5. Export glTF | `$B -b scene/out/gallery_baked.blend -P scene/export.py` | 30 s |
| 6. Compress for the web | `node scene/tools/optimize.mjs` | 1 min |
| 7. Prefilter the reflection maps | `node scene/tools/pmrem.mjs` | 10 s |
| 8. Poster still (with the site running) | `node scene/tools/poster.mjs http://localhost:3002/` | 30 s |

Re-bake a single group after a small change: `-- --only vault,furniture_b`.
Pass `-- --web` to `build_scene.py` to also write the website's `path.json`;
without it the path goes to `scene/out/` so the live site keeps matching its
baked model while rooms are being changed.

The artworks are generated too, with no image assets: `lib/art.py` paints each
one from a style, a palette and a seed (the vault's works carry gold leaf, with
their own roughness map), and `lib/collection.py` lists what hangs where (wall,
position, size, mount), with the hang explained at the top. They are built into
their own bake group, `art`, with a ceiling spot per work aimed 30 degrees off
vertical (two for the widest). The vault door opens onto a small room cut into
the black volume, where the three gilded works hang. To change a work, edit its
row in `collection.py` and rebuild; to preview the whole set as a contact sheet
without building the scene, call `art.make(...)` for each row of `WORKS`.

The walk ends on the roof. The beige room's stairs turn at a landing in the far
corner and climb the right wall through an opening in the ceiling (twenty
19.75 cm risers, `ROOF_Z` = 3.95 m) into the rooftop hall, built on top of
frame B: white walls, a 6 m ceiling with beams and a luminous panel, two
freestanding walls, sculptures on plinths, and a glass wall onto a terrace and a
city skyline at dusk (`tex.city_night`, an emissive map tiled along a very wide
plane far off). Its works hang like the others (walls `hall_n`, `hall_w`,
`part_1`, `part_2`; `WALL_FLOOR` lifts them and the camera to the roof) and bake
into their own groups: `roof` (the hall), `art_roof` (its works) and `sky` (the
luminous panel and the skyline, which are emissive and need no light).

The vault door (`vault_door` collection, tagged `door`) is not baked: the
website hangs it on a pivot at its hinge and swings it closed/open by scroll
progress, with smoke from the opening (`src/components/gallery/vault.js`).
The hinge, swing and open window are written to `path.json` under `vault`.

Outputs used by the site:

- `public/gallery/model/gallery.glb` geometry + material textures
- `public/gallery/lightmaps/*.webp` baked light per group (8-bit, scaled)
- `public/gallery/env_a.pmrem.hdr`, `env_b…`, `env_c…` reflection maps (dark gallery, frame B, rooftop hall),
  prefiltered by `pmrem.mjs` from the baked `env_*.hdr` panoramas (512 x 256)
- `src/components/gallery/poster.webp` the real first frame, captured from the site by `poster.mjs` (2400 x 1200,
  imported by `GalleryHero.jsx` so its URL is content-hashed and never served stale),
  shown until the 3D view is ready (use a production build: the dev server adds its badge)

## Loading and frame rate

The hero has to open smoothly on ordinary laptops (integrated GPUs, high-DPI
screens), so `src/components/gallery/Scene.jsx` keeps the GPU and main thread light:

- every download starts at once (and `GalleryHero.jsx` starts them before the 3D code arrives)
- no post-processing pass: AgX tone mapping and the contrast grade run in each material's own
  shader, the vignette is a CSS overlay
- reflection maps arrive prefiltered, so the browser never runs three.js's PMREM filter
- while the poster is up: shaders compile in parallel, textures upload a few milliseconds per
  frame, and one object per shader variant is drawn once (many drivers only finish a shader at
  its first draw), so nothing compiles or uploads once the walk starts
- rooms that walls and floors hide are not drawn (path.json `zones`, from `build_scene.py`)
- canvas resolution starts at one pixel per CSS pixel and rises to the screen's density only
  while frames hold 60 fps; texture anisotropy is 2x
- visitors are animated and drawn only within 16 m of the camera
- `src/components/gallery/data/path.json` camera path, each work's eye icon and details (placeholder credits from `lib/collection.py` `CREDITS`)
- `src/components/gallery/data/lightmaps.json` lightmap files and intensities

The camera path is defined once in `build_scene.py` (`keys`) and interpolated
identically in Blender (`lib/camera_path.py`) and the browser (`path.js`).
It passes square on to every artwork without stopping: `art_view` places the
camera far enough back to fit a work with a margin, and `STEPS` lists the keys
with the time between them. The walk's length (`WALK`), the Rooms menu stops,
the point where the rooms turn light and each work's eye icon (where it sits,
when it shows, its credits) are written to `path.json` too, so the site
follows any change to the path. Hovering an eye (tapping, on a touch screen)
opens that work's details.

The path is composed for a 4:3 screen. On portrait screens and phones on
their side the site refits it (`src/components/gallery/framing.js`): it widens
the lens and steps the camera back (never through a wall) until each work fits
the part of the screen the header and Rooms bar leave clear. Desktop and tablet
views are used exactly as designed.

## Visitors

The people standing and sitting in the rooms are Microsoft Rocketbox avatars
(MIT, see `public/gallery/people/LICENSE.txt`), each playing a motion-captured
idle clip. They are not part of the Blender build: `scene/people/` turns them
into small glTF files with Node, Python (Pillow) and a headless browser
(Playwright), no Blender needed.

```bash
# the cast's avatars and clips only (the full library is several GB)
git clone --depth 1 --filter=blob:none --sparse https://github.com/microsoft/Microsoft-Rocketbox rocketbox
git -C rocketbox sparse-checkout set --no-cone \
  '/Assets/Avatars/Adults/<avatar>/Export/<avatar>.fbx' '/Assets/Avatars/Adults/<avatar>/Textures/*.tga' \
  '/Assets/Animations/all_animations_max_motextr_static/<clip>.max.fbx'   # one pair per cast.json entry
python3 scene/people/textures.py rocketbox/Assets
node scene/people/bake.mjs rocketbox/Assets
```

Both take visitor ids after the Assets folder to (re)bake only those, for
example `node scene/people/bake.mjs rocketbox/Assets bench bronze`. With
`CHROME` set to an installed Chrome, `bake.mjs` uses it instead of
Playwright's own Chromium (then only the `playwright` package is needed).
On Windows Git Bash, set `MSYS_NO_PATHCONV=1` before `sparse-checkout set`,
or the leading-slash patterns are rewritten into Windows paths.

`cast.json` says which avatar and clip each visitor is; `bake.mjs` writes
`public/gallery/people/<id>.glb` (about 8k triangles and 600 KB each). Where
they stand, what they look at and how they are lit is set on the website, in
`src/components/gallery/visitors.js`: nobody stands between the camera and a
work it stops at, and the phone framing keeps its camera clear of them. The
visitors downstairs are prepared with the rooms, before the poster lifts; the
rooftop's (`env: "c"`) are fetched only once the gallery is showing, since the
walk reaches them last. They share the shaders of the ones below, so they cost
no shader compile when they come into view.
